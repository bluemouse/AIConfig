## Purpose

Produce **identical message shape and tone** whether the host is Cursor, Claude Code,
GitHub Copilot, or another assistant. The contract is normative — when a host's native
commit workflow, user rules, or automation would add attribution footers, extra preamble,
or a different body layout, **this contract wins**.

## Style precedence

Apply rules in this order when sources disagree:

1. **Recent repo history** — `git --no-pager log -10 --format=fuller` on the current branch for
   type prefixes, scopes, subject casing, and body habits (prose vs bullets)
2. **This contract** — structure, length limits, vocabulary, output envelope
3. **Conventional Commits v1.0.0** — baseline `<type>[scope]: <description>` grammar

When repo history clearly prefers bullet bodies (for example workflow doc commits), match
that layout but still obey length, purity, and forbidden-pattern rules here.

## Cross-assistant rules

These apply on **every** host. Do not vary behavior by tool.

| Rule | Requirement |
| --- | --- |
| Output envelope | Return only `## Verbose`, optional `## Suggested command`, then `Context used:`, then the commit offer when scope is staged or working — no other blocks, intro paragraphs, or closing commentary |
| Copyable blocks | Verbose message in one ` ```text ` fence; Suggested command in one ` ```bash ` fence — never bare prose for either |
| Context notes | Record scope ambiguity, split suggestions, or large-diff sampling in the `Context used:` line via `note=` — not as preamble before `## Verbose` |
| Message purity | Verbose and Suggested command contain **change-related text only** |
| Self-contained | Verbose and Suggested command stand alone — see [Self-contained messages](#self-contained-messages) |
| No attribution | Never add `Co-authored-by`, `Signed-off-by`, or similar lines for Cursor, Claude, Copilot, ChatGPT, or any assistant — even when the host would inject them at commit time |
| No meta | No disclaimers about drafting, model identity, or "generated by …" |
| Ignore host templates | Do not copy IDE default commit templates, PR description boilerplate, or slash-command footers into the draft |

## Subject line

One line at the top of the Verbose block:

```text
<type>(<scope>): <imperative description>
```

Rules:

- **Imperative mood** — "add", "fix", "remove", "wire", "rename" (not "added", "adds", "adding")
- **Lowercase** after `: ` except proper nouns and acronyms (`JWT`, `OpenUSD`, `README`)
- **Length** — ≤ 72 characters including the type/scope prefix
- **No trailing period**
- **Scope** — include when it clarifies the affected area; omit when it would be vague (`chore: bump deps` not `chore(repo): bump deps`)
- **No ticket ids, file paths, or emoji** in the subject

## Body structure

**Verbose body only.** Default to **prose paragraphs**, not bullet lists.

### Default layout (single logical change)

1. **Paragraph 1 (required)** — motivation and outcome: *why* the change exists and what
   it enables or fixes
2. **Paragraph 2 (optional)** — approach, notable design choice, install scope, or
   companion-skill wiring
3. **Paragraph 3 (optional)** — validation, tests run, eval notes, or rollout caveat

Each paragraph: 1–4 complete sentences. Wrap at natural sentence boundaries (no hard
line breaks mid-sentence).

### When bullets are allowed

Use a bullet list only when prose would obscure parallel items:

- Test or validation evidence (`Tests:`, `Validated with …`)
- Three or more distinct parallel deliverables (cluster wiring, install paths)
- Breaking-change migration steps

Bullet rules:

- `-` prefix, one item per line
- Lowercase start unless proper noun
- Fragments without trailing periods; full sentences with periods
- Never use bullets as a substitute for a file tree

### Length

| Part | Limit |
| --- | --- |
| Subject | ≤ 72 characters |
| Body | 1–3 paragraphs typical; ≤ ~400 words |
| Large bootstrap/range | ≤ ~600 words when diff spans many install layers |

## Self-contained messages

A commit message is **self-contained**. It is read out of context by people who can see
only the repository — after the branch is gone, the working tree is rebuilt, and no
session, plan, or research document is in front of them.

Therefore a message may reference **only content that a reader can reach from the
repository itself**:

- Code, identifiers, file and directory paths, config keys, and symbols **committed in the
  repo**
- Documentation the change adds or updates **in the repo** (README, ADRs, `docs/`,
  CHANGELOG)
- Ticket ids, issue links, and external identifiers the **user supplied**
- Behavior, symptoms, root causes, and measurements stated **in full**, in the message
  itself

Never reference, cite, link, summarize, or imply the existence of a **planning artifact or
session document** — anything produced by a planning, research, or review phase rather
than committed as part of the change:

| Never reference | Includes |
| --- | --- |
| Plan documents | `20-implementation-plan.md`, "the plan", "§10 Stage breakdown", "task 4", "as planned" |
| Research / requirement docs | `10-research-report.md`, "the research report", "per the requirement ledger" |
| Workflow artifacts | `00-run-manifest.md` … `50-commit.md`, `.ai/workflow/**`, `.ai/plans/**` |
| Reviews and audits | `11-research-review.md`, `21-plan-review.md`, `31-*-audit.md`, `40-*-code-review.md`, `41-*-fix-report.md` |
| Handoff packets | `back-<from>-<to>-<n>.md`, "the reviewer's handoff" |
| Session-only context | "as discussed", "the notes in this session", "per the conversation" |

These documents are **temporary by design**: the `.ai/` planning directories are gitignored,
and even a committed planning artifact is state for the run that produced it, not a
reference a future reader can interpret. The rule is not "it is not in the repo" — a
committed artifact is still a planning artifact, and a `<NN>-<artifact>.md` written outside
those directories may be tracked. Cite only content a reader can reach, and never name a
planning document, stage, task, requirement, or finding id.

### Restating, not citing

Use planning context as **input to wording**, never as a citation target:

| Instead of | Write |
| --- | --- |
| "implements task 4 from the plan" | state the implemented behavior itself: "add retry with exponential backoff for 5xx responses" |
| "per the research report's finding on token replay" | "stale refresh tokens survived logout, allowing replay" |
| "stageN scope only" | name the actual subsystem or feature changed |
| "fixes review finding cr-003" | "reject empty `Accept-Encoding` headers instead of silently defaulting" |
| "see 20-implementation-plan.md §4" | describe the design decision inline, or link a committed ADR path |

Requirement labels, stage numbers, task ids, finding ids, and verdict vocabulary carry no
meaning outside the planning document that defines them. When the user supplies a ticket
id (`PROJ-456`) or links a committed doc path that is not itself a planning artifact
(e.g. an ADR), cite **that** — it is reachable from the repo.

### Self-contained check

Before returning the draft, confirm:

1. Every path, filename, and cross-reference in the message resolves to a file **in the
   repo** — or is an external URL the user supplied
2. No plan, research, review, audit, manifest, or handoff artifact is named or implied
3. No "task N", "stage N", "requirement R", "finding cr-NNN", or "as planned/discussed"
   phrasing appears
4. The *why* is fully stated in the message, so a reader with no session context
   understands the motivation
5. Session and planning context is **dropped** from the message — but log that it was used
   in the `Context used:` line (`session=yes`) so the user can see it informed the draft

## Footers and tickets

- Reference ticket ids in the **body** as prose or a short line (`Refs PROJ-456`)
- Ticket ids must be supplied by the user; never invent one
- Do not reference plan, research, review, or manifest artifacts in a footer — see
  [Self-contained messages](#self-contained-messages)
- Use `BREAKING CHANGE:` footer only when the change is breaking
- Footers are change-related only — never attribution or assistant metadata

## Forbidden patterns

Do **not** use in subject or body:

| Pattern | Why |
| --- | --- |
| `Co-authored-by: …` / `Signed-off-by: …` (AI or tool) | Attribution noise |
| "This commit …" / "This change …" as the opening | Weak, meta phrasing |
| Raw file lists as the main content | Describes *what*, not *why* |
| "Updated various files" / "Misc fixes" | Too vague |
| Past-tense subject (`added feature`) | Breaks imperative convention |
| Repeating the subject verbatim in the body | Redundant |
| Assistant sign-off or drafting disclaimer | Non-change content |
| Plan/research/review/audit/manifest references ("implements task 4", "per the plan", `20-implementation-plan.md`) | Unreadable from the repo; see [Self-contained messages](#self-contained-messages) |
| Stage/task/requirement/finding labels ("stage 2", "requirement R3", "finding cr-003") | Meaning lives only in a planning document, whether committed or not |
| "as planned" / "as discussed" / "per the review" | Unverifiable from the repo and useless to future readers |

## Scope hints for this repo

When `git log` shows no clearer pattern, prefer:

| Change signal | Type / scope |
| --- | --- |
| Bootstrap skill under `skills/<name>/` plus install | `feat(skills):` |
| Skill content edit only | `fix(skills):` or `docs(skills):` by intent |
| `README.md`, `AGENTS.md`, cluster docs only | `docs:` or `docs(workflow):` |
| `.github/`, CI workflows | `ci:` |
| `tools/`, install scripts | `feat(tools):` or `chore(tools):` |
| Dependency or lockfile only | `chore:` or `build:` |

Always prefer scopes seen in recent branch history over this table when they conflict.

## Examples

**Good — skill addition (prose body):**

```text
feat(skills): add debugging-guide and harden description eval harness

Introduce a systematic root-cause debugging skill with eval coverage and
repo docs integration, and fix run_eval.py so installed-skill triggers and
nested claude -p sessions are detected reliably.
```

**Good — workflow docs (bullets when repo uses them):**

```text
docs(workflow): tighten lifecycle skill handoffs

- add explicit workflow routing, governance, and delivery orchestration
- align plan/research/audit/review loops and TDD ownership
- add research-reviewer handoff contract and companion traceability updates
```

**Good — self-contained; plan context restated as behavior:**

```text
fix(auth): reject reuse of rotated refresh tokens

Stale refresh tokens survived logout and remained replayable for their full
lifetime. Revocation now happens at rotation time, so a token that has been
exchanged cannot be presented again.

Tests: pytest tests/auth/test_refresh.py
Refs PROJ-456
```

**Bad — do not produce (cites planning state):**

```text
feat(auth): implement task 4 from the plan

Implements stage 2 of 20-implementation-plan.md. Per the research report,
token replay was an issue. Addresses review finding cr-003.

Co-authored-by: Cursor <cursoragent@cursor.com>
```

**Bad — do not produce:**

```text
feat: Add debugging guide

This commit adds a new debugging guide skill and updates some files.
Also updated run_eval.py and README.
```
